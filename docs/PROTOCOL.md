# Local bridge protocol (version 2)

`state.json` is atomically replaced for every valid CommunicationMod frame. It contains the original mod state plus `protocol_version`, monotonic `state_seq`, `phase`, `decision_id`, `legal_actions`, and stable-ID `options`. Cards expose `card_instance_id`; combatants expose `enemy_instance_id`; potions expose `potion_instance_id`.

Write exactly one JSON object atomically to `command.json`. Every state-changing request must carry `policy_version=fast-policy-v5`, plus `expected_seq`, `decision_id`, and `phase` copied from the latest `state.json`. Once `in_game=true`, it must also carry the exact `attempt_id`, `run_id`, `seed`, `character`, `ascension_level`, `run_type`, `decision_hash`, `controller_hash`, `policy_version`, and `selection_id` projected by the active state. The first authoritative frame after `START` is the only projection window: if the controller has just durably created `run-context.json`, `stsctl` may source those fields only after validating that context's complete selection binding against the frame's class, seed, A0 level, standard-run flag, and derived run ID. Callers may never self-report attempt fields. Read-only `STATE` is exempt; `MAIN_MENU` `START` instead uses the selector/pre-run binding contract. Choices use `option_id`; plays use `card_instance_id` and, when required, `enemy_instance_id`. Both the client and bridge reject missing or different bindings before a raw game command is emitted. The bridge resolves stable IDs against the current state and only then converts them to CommunicationMod indexes.

Example:

```json
{"id":"uuid","action":"choose","policy_version":"fast-policy-v5","expected_seq":42,"decision_id":"decision:...","phase":"GRID","attempt_id":"attempt-...","run_id":"IRONCLAD:0:123","seed":123,"character":"IRONCLAD","ascension_level":0,"run_type":"standard","decision_hash":"...","controller_hash":"...","selection_id":"selection-...","option_id":"option:...","choice_index":2}
```

`action-receipt.json` is also atomically replaced. Rejected requests have `status: rejected` and are never sent to the game. Accepted requests are finalized after the next mod frame with `requested_target_id`, `resolved_target_id`, `accepted_state_seq`, `result_state_seq`, `success`, and `error`. A controller must not issue the next action until the final receipt matches the new state and requested/resolved IDs are identical.

A later frame completes a state-changing action only when it is ready for a new command and either its `decision_id` differs from the decision that accepted the request or it proves the exact target-specific effect. For `GRID` and `HAND_SELECT`, the requested `card_instance_id` appearing in authoritative `screen_state.selected_cards` is such proof even if the screen keeps the same decision ID; a different selected instance never completes the receipt. Non-ready frames are ignored. An unchanged ready frame without exact effect proof is resynchronized with `STATE`; after three unchanged authoritative frames the action fails instead of remaining permanently `accepted`. CommunicationMod also has a stable-state fallback publication, while asynchronous combat-reward and grid selections remain blocked until their exact selected objects are consumed.

Combat frames whose living monsters still report the temporary `DEBUG` intent are not decision states. The bridge marks them `COMBAT_INITIALIZING`, exposes only `wait`/`state`, and advances frames internally while an action receipt is pending. A normal gameplay command cannot be issued until real monster intents are available.

Potion requests bind the potion slot by `potion_instance_id`. A targeted use must bind exactly one live, non-`half_dead`, non-`is_gone` enemy. Discards and non-targeted uses reject any supplied `enemy_instance_id` instead of silently ignoring it.

EVENT options bind by their explicit enabled `choice_index`, never by the order of `screen_state.options`. A missing or duplicate index produces an unbound target and is not auditable. On Neow's actual reward activation page (`screenNum=3`), CommunicationMod emits `neow_contract` only when every enabled button has a unique exact `NeowReward.optionLabel` match and the enabled-button/reward counts agree. The contract contains enum-backed `reward_kind` and `drawback_kind` plus reflected `hp_bonus`, `cursed`, and `drawback_def_kind`; localized text is only a join key and is not mechanics evidence. Reward/container order is not semantic. Missing reflection fields, count disagreement, duplicate labels, or any other ambiguity omits the contract and therefore blocks a clear audit.

A one-button Neow intro/continuation/dismissal at any reflected non-activation `screenNum` is typed as `NEOW_DIALOG_ADVANCE` with `resource_effect=NONE`. It is never rebound to a reward merely because the private reward list already contains one item. Multi-button non-activation screens remain untyped. The bridge validates the complete contract shape and known enum domain, forwards it in the option target, and derives `mechanism_id` only from that canonical contract; it never derives mechanics from translated text or invents a random outcome.

The single bridge-owner claim uses a strict owner-token lease inside `bridge-instance.json.claim-lock`. A live owner, a fresh ownerless mkdir/write window, unverifiable process state, or malformed/unexpected lock content fails closed. A dead owner may be recovered; an ownerless lock may be recovered only after the bounded stale interval and only when no live bridge instance exists. Recovery and release re-read the exact owner token before deletion, so an old claimant cannot remove a later claimant's lease.

Across a bridge restart, the next `state_seq` resumes after the maximum valid sequence found in `state-meta.json` and `state.json`. This preserves monotonicity if the prior process stopped after atomically publishing the state but before updating its metadata sidecar.

Supported actions: `start`, `resume`, `choose`, `play`, `potion`, `end`, `proceed`, `return`, `wait`, and read-only `state`. `resume` is legal only at the main menu, must bind `resume:<CLASS>:autosave`, and is rejected unless the latest state explicitly reports that character's autosave.
